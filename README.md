# ImageFlow

> **Note:** This README was generated by an AI from the project headers and source.

A C image processing library with heterogeneous compute support. Devices, operations, and schedulers are all registered into runtime dispatch tables at load time, so adding a new backend, a new operation, or a new scheduler no longer means touching a hand-written switch statement — you add an entry to a `.def` file and drop in an implementation.

## Features

- GPU-accelerated image processing via CUDA and HIP (AMD ROCm)
- OpenMP CPU fallback when no GPU is available
- Device-agnostic dispatch — devices (`CPU`, `CUDA`, `HIP`, ...), operations (`GRAYSCALE`, `INVERT`, `BRIGHTNESS`, ...), and schedulers (`CPU`, `LINEAR`, `REORDER`, ...) are all driven by X-macro `.def` lists, so new ones can be added without touching the scheduler-dispatch, pipeline, or op-dispatch code
- Self-registering backends and schedulers — each backend registers its device availability and its per-op implementations, and each scheduler registers its execute function, via load-time constructors (`IF_CONSTRUCTOR`) — no manual wiring or init calls required
- Pipeline API — build a sequence of operations, run them against an image in one call
- Automatic device management — host↔device transfers are handled generically at device-boundary crossings inside the scheduler via a per-device load/retrieve/free dispatch table; callers don't touch device memory directly
- Pipeline reordering optimizer — reorders operations before execution to minimize host↔device transfers, generalized to any number of devices, with four aggression levels (safe → stencil → reduction → morph), selectable at runtime via an environment variable
- Runtime-selectable default scheduler and reorder aggression via environment variables — no rebuild needed to switch strategies
- Registering a device or an operation gets you test coverage for free — see [Testing](#testing)
- C11 core with C++ support for GPU backends

## Building

### Requirements

- CMake ≥ 3.20
- A C11 compiler
- OpenMP (optional but recommended)
- CUDA toolkit (optional)
- ROCm / HIP (optional)

At least one of CUDA or HIP is needed for GPU acceleration. If neither is found, the build falls back to OpenMP only. Even when built in, CUDA/HIP devices are only actually used if a GPU is detected at runtime — each backend probes its own availability on startup and enables or disables itself accordingly.

### Steps

```bash
cmake -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug -j$(nproc)
```

CMake will automatically detect CUDA and HIP and enable them if found. No flags needed.

This builds two library targets side by side into `build/<debug|release>/`:

| Target | Output | Notes |
|---|---|---|
| `imageflow_static` | `libImageFlow.a` | Built PIC, so it's safe to link into a `.so` later (e.g. the pybind11 test module below). Self-registering translation units (devices/ops/schedulers) only survive in a static archive if the *consumer* links with `--whole-archive` — `target_link_whole_archive()` in `CMakeLists.txt` does this for you. |
| `imageflow_shared` | `libImageFlow.so` | Every object file is always included in a shared library, so no whole-archive juggling is needed downstream. |

Both variants get identical compile settings (`imageflow_apply_build_settings()` in `CMakeLists.txt`), so debug/release behavior doesn't depend on which one you link against. `BUILD_TESTS` (default `ON`) additionally builds `libImageFlow_tests.a` — see [Testing](#testing). Standard `install(...)` targets are provided via `GNUInstallDirs`.

## API

### Image I/O

```c
#include <ImageFlow/io/image.h>

IF_image_t img;
IF_loadImage(&img, "photo.jpg");
// ... process ...
IF_storeImage(&img, "out.jpg");
IF_freeImage(&img);
```

`IF_image_t` holds pixel data as a normalized `float*` buffer (values in `[0.0, 1.0]`) with width, height, and channel count. Supported formats: PNG, BMP, JPG/JPEG.

`IF_storeImage` writes at the default quality (`IF_STD_QUALITY`, 90). For explicit control over JPEG quality, use `IF_storeImageQ(img, path, quality)` — `IF_storeImage` is just a thin wrapper around it.

### Pipeline

Operations are queued into an `IF_Flow_t` pipeline and executed in one call against an image. Builder functions are generated automatically from `operations/operations.def`, one per registered operation:

```c
#include <ImageFlow/pipeline.h>
#include <ImageFlow/scheduler/scheduler.h>

IF_image_t img, img_out;
IF_CHECK(IF_loadImage(&img, "img.jpg"));

IF_Flow_t flow;
IF_flow_init(&flow);

IF_flow_Invert(flow);
IF_flow_Grayscale(flow);
IF_flow_Brightness(flow, 0.5f);

IF_CHECK(IF_flow_run(flow, &img, &img_out));
IF_CHECK(IF_storeImage(&img_out, "out.jpg"));

IF_flow_free(flow);
IF_freeImage(&img);
IF_freeImage(&img_out);
```

`IF_flow_run` hands the pipeline off to a scheduler. The scheduler is responsible for:

- checking, per operation, whether its preferred device is enabled and has a registered implementation, falling back to CPU otherwise
- managing host↔device transfers generically at device-boundary crossings, via the per-device load/retrieve/free dispatch table
- optionally reordering operations to minimize those transfers
- executing each operation via the dispatch layer

A specific scheduler can be selected explicitly:

```c
IF_CHECK(IF_flow_run_sched(flow, &img, IF_SCHEDULER_REORDER, &img_out));
```

### Schedulers

| Scheduler | Description |
|---|---|
| `IF_SCHEDULER_CPU` | CPU-only execution via OpenMP; skips GPU dispatch entirely |
| `IF_SCHEDULER_LINEAR` | Naive sequential scheduler; runs operations in pipeline order and transfers data at device boundaries. Reference implementation and the baseline against which `IF_SCHEDULER_REORDER` is validated |
| `IF_SCHEDULER_REORDER` | Reorders the pipeline at a configurable aggression level (see below), then runs linearly. **Default.** |

Schedulers are registered the same way as devices and operations: each scheduler self-registers its implementation into a dispatch table (`IF_sched_impls[]`) via a load-time `IF_CONSTRUCTOR`, driven by the X-macro list in `scheduler/schedulers.def`. `IF_flow_run_sched` simply bounds-checks `sched` and looks up `IF_sched_impls[sched]` — there's no hand-written switch statement to update when adding a scheduler.

`IF_SCHEDULER_REORDER` is backed by `IF_reorder`, which groups operations by device affinity within runs of non-barrier ops to minimize host↔device transfers without changing observable output. Its sort key is device-count agnostic: instead of a single GPU/CPU polarity flip, the device ordering itself is reversed on odd-priority tiers, so the device at the boundary between two tiers always matches on both sides — this generalizes cleanly to any number of registered devices.

`IF_reorder` accepts an `IF_ReorderLevel_t` aggression level, controlling which operation types are allowed to cross segment barriers:

- **`IF_REORDER_SAFE`**: only POINT and METADATA ops are reordered — these are trivially commutative. Default aggression.
- **`IF_REORDER_STENCIL`**: additionally allows POINT ops to cross STENCIL barriers
- **`IF_REORDER_REDUCTION`**: additionally allows POINT ops to cross REDUCTION barriers
- **`IF_REORDER_MORPH`**: additionally allows POINT ops to cross MORPH barriers — use only if you understand the commutativity implications

### Environment variables

Two environment variables let you change scheduling behavior at runtime, without recompiling:

| Variable | Affects | Values | Default |
|---|---|---|---|
| `IF_SCHED` | Which scheduler `IF_flow_run` (the no-argument entry point) uses | Any registered scheduler name — `CPU`, `LINEAR`, `REORDER` (matched via `IF_strsched`, case-sensitive, must match exactly) | `REORDER` |
| `IF_AGGRESSION` | Reorder aggression used by `IF_SCHEDULER_REORDER` | `O0`/`SAFE`, `O1`/`STENCIL`, `O2`/`REDUCTION`, `O3`/`MORPH` | `SAFE` (`O0`) |

```bash
# Force the naive sequential scheduler
IF_SCHED=LINEAR ./your_app

# Use the reorder scheduler at the most aggressive level
IF_SCHED=REORDER IF_AGGRESSION=O3 ./your_app
# equivalently:
IF_SCHED=REORDER IF_AGGRESSION=MORPH ./your_app
```

If the variable is unset, or set to a value that doesn't match any registered scheduler name / recognized aggression alias, the default is used silently.

`IF_flow_run_sched(flow, img_in, sched, img_out)` always honors the explicit `sched` argument you pass and ignores `IF_SCHED` — the environment variable only affects the zero-argument `IF_flow_run` convenience wrapper. `IF_AGGRESSION` is read only by `IF_SCHEDULER_REORDER`'s registered implementation; if you call `IF_reorder` directly with an explicit `IF_ReorderLevel_t`, that call also bypasses `IF_AGGRESSION`.

#### Available operations

Defined in `include/ImageFlow/operations/operations.def` as `IF_OP_DEF(id, name, traversal_type, args)`:

| Builder function | Description |
|---|---|
| `IF_flow_Grayscale(flow)` | Rec. 601 luminance grayscale |
| `IF_flow_Invert(flow)` | Per-channel inversion (v' = 1 - v) |
| `IF_flow_Brightness(flow, factor)` | Multiply channels by factor, clamped to 1.0 |

### Devices

Defined in `include/ImageFlow/devices/devices.def`. Currently `CPU`, `CUDA`, and `HIP`. Each backend registers its own availability at load time (e.g. the CUDA backend probes `cudaGetDeviceCount` in a constructor and enables/disables `IF_DEV_CUDA` accordingly); the CPU backend is always enabled. `IF_enabled_gpu()` returns the first enabled GPU device, falling back to `IF_DEV_CPU` if none is available.

### Extending ImageFlow

Adding a new device, operation, or scheduler is table-driven — no dispatch, pipeline, or scheduler-selection code needs to change, and devices/operations automatically pick up test coverage too. See [CONTRIBUTING.md](CONTRIBUTING.md) for the walkthrough.

### Error handling

All functions return `IF_error_t`. The `IF_CHECK` macro propagates errors with file and line information:

```c
IF_CHECK(IF_loadImage(&img, "photo.jpg"));
```

On error it prints to stderr and returns from the calling function. For manual inspection:

```c
const char *msg = IF_strerror(err);
IF_logError(stderr, err);
```

## Testing

Test sources live under `tests/src/*.c` and are picked up automatically — `tests/CMakeLists.txt` globs that directory, so dropping in a new `.c` file is enough to get it built and run. No CMake changes needed.

Tests are written against [fastest](https://github.com/danielesavino/fastest), vendored as a git submodule at `tests/vendor/fastest`:

```bash
git submodule update --init --recursive
```

Two headers under `tests/include/IF_tests/` bridge ImageFlow's `IF_error_t` world into fastest test bodies:

- **`IF_tests/error.h`** — `IF_FASTEST_CHECK(expr)` evaluates an `IF_error_t`-returning expression inline; on failure it logs the error (file/line-annotated, via `IF_logError`), maps it onto the closest `FASTEST_ERROR_*` exit code, and returns out of the enclosing test.
- **`IF_tests/utils.h`** — `PROBE_DEV(out, dev)` marks a test skipped (not failed) if `dev` isn't enabled at runtime; `CHECK_IMPL(impl, dev)` does the same when an op has no registered implementation for a device.

### Registering a device or op automatically adds tests

Because `tests/src/devs.c` and `tests/src/ops.c` X-macro over the same `.def` files the library itself uses, adding an entry to `devices.def` or `operations.def` doesn't just wire the new device/op into the dispatch tables — it generates test coverage for it too, with no extra test code required:

- Every device in `devices.def` gets a `devs/<name>/round_trip` test (host → device → host → store → reload → compare within tolerance) and a `devs/<name>/double_free` test, generated by `tests/src/devs.c`.
- Every operation in `operations.def` gets an `ops/<name>/check_against_cpu` test, generated by `tests/src/ops.c`, which runs the op on every enabled device and diffs the result against the CPU reference implementation.

Both use `PROBE_DEV`/`CHECK_IMPL` to skip rather than fail when a device isn't present on the current machine or an op has no implementation for it — so the suite runs the same (with skips) whether or not GPU hardware is available.

### Building and running

Test build is on by default (`BUILD_TESTS=ON`):

```bash
cmake -B build/debug -DCMAKE_BUILD_TYPE=Debug
cmake --build build/debug --target imageflow_static imageflow_tests_static
```

This produces `build/debug/libImageFlow.a` and `build/debug/libImageFlow_tests.a`. Tests aren't run as a standalone C binary — fastest links them into a Python extension module via pybind11, and the suite is driven from Python:

```bash
./scripts/build_wheel.sh debug     # or: release
python3 tests/main.py
```

`scripts/build_wheel.sh` takes the built static archives (`FASTEST_USER_LIB=libImageFlow_tests.a`, `FASTEST_EXTRA_LIBS=libImageFlow.a`) and `pip install -e`s them as a Python module named `IF_tests` (`FASTEST_MODULE_NAME`) via fastest's own `bindings/` build flow. `tests/main.py` then imports both `fastest` and `IF_tests`, sets `IF_tests` as fastest's backend, and runs the whole suite with `fastest.run_log_all()`.

## Notes

- **Multi-GPU / cross-accelerator parallelism** (e.g. NCCL-style same-vendor multi-GPU) is not planned. Dispatch is no longer hardcoded to "one GPU" though — the scheduler can route each operation to whichever registered device it prefers, and the goal is to extend this toward single-wafer-scale chips, not to fan work out across multiple same-vendor accelerators in parallel.
- **HIP/ROCm** support is low-maintenance — the backend exists but is not actively tested due to lack of AMD hardware.
- **Intel GPU / oneAPI / SYCL** support is not planned.
- **MPI / distributed execution** is not planned. Adding it would require reworking `IF_OpArgs_t` and the dispatch model, since it currently assumes pointer arguments stay local to one process (see the warning in `op_args.h`).
